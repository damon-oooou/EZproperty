## 与实施方案的偏差（实现时拍板，理由如下）

| 方案原文 | 实现 | 原因 |
|---|---|---|
| 跨 agency 返回 403 | **404** | `TenantGuard` 的既有约定：不属于你的资源 = 404，不泄露 id 存在。`TenantGuard` 本身未改；photo 级端点走 photo → room → property 用它公开的 `check(Property)` |
| 来源 = 最早 `inspection_date` 的 inspection | **最早引用该照片的 join 行**（`inspection_photos.id` 最小） | 用户可以给 inspection 倒填日期，同一天也可能两次；join 行创建顺序才是"谁先拥有这张照片"。正常情况结果一致 |
| `carried_forward` 不回填 | **V13 回填**：每张照片 id 最小的 join 行为原始上传，其余标 TRUE | 不回填则现有数据的沿用照片全被 History 归为 "Newly captured"，PDF 永不标 Carried forward。v0.8 前照片出现在多个 inspection 的唯一途径是继承，回填是确定的 |
| `confirmed_at` 用 `Instant` | `LocalDateTime` | `ddl-auto: validate` 下 `Instant` 映射带时区 timestamp，与 `TIMESTAMP` 列校验不过 |
| 更新端点：先入库再 set `replaces_photo_id` | note / replaces **随 INSERT 一起写入** | UNIQUE 冲突在 INSERT 处立刻抛出，走既有"失败即清理三档文件"路径；否则并发 409 会留孤儿文件 |
| 更新端点 note 在 API 层可选 | **API 层必填**（空 → 400） | 方案自己的理由（没有说明的替换半年后无法解读）对 API 同样成立，iOS 不该绕过 |
| PDF note 截断或换行二选一 | 换行不截断 | 报告是证据文件，截掉说明比多占几行更糟 |
| — | `PhotoResponse` 增加 `carriedForward` | 方案已要求 lightbox 显示来源；没有这个字段分不清沿用还是本次新拍 |
| — | 照片网格改为按 photo id 排序 | 原查询无 ORDER BY，顺序由存储决定 |
